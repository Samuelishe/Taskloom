# Контекст продолжения работы

## Назначение

Этот документ нужен для продолжения работы над проектом после потери текущей сессии. Новый исполнитель должен сначала прочитать этот файл, затем `ProjectOverview.md`, `Architecture.md`, `DevelopmentPlan.md`, `Decisions.md` и `WorkLog.md`.

## Что это за проект

Taskloom - персональное desktop-приложение для Windows, ориентированное на календарь и работу с разными типами записей, привязанными ко времени и датам.

Это не обычный todo list и не простое notes app. Базовая модель проекта должна строиться вокруг календарной записи, а не вокруг одной сущности задачи.

## Технологические ограничения

- C#
- .NET 10
- WPF
- MVVM
- CommunityToolkit.Mvvm
- SQLite
- Dapper

## Внешние зависимости запуска

- Проект собирается под `net10.0-windows10.0.19041.0`.
- Для запуска пользователю нужен установленный .NET 10 Desktop Runtime.
- Для Windows notifications через `AppNotificationManager` нужен установленный Windows App Runtime 1.8.
- Если Windows App Runtime 1.8 отсутствует или установлен неполно, приложение не должно падать: используется fallback через tray balloon.
- Для audio metadata и cover art используется пакет `TagLibSharp`.

Нельзя без серьёзной причины переводить проект на:

- web stack
- MAUI
- WinUI
- heavy frameworks
- EF Core

## Правила реализации

- Не переопределять базовые решения проекта без серьёзной причины.
- Работать строго пошагово.
- Не создавать лишние абстракции.
- Не переносить бизнес-логику во View.
- Использовать MVVM последовательно.
- Использовать `ObservableObject`, `ObservableProperty`, `RelayCommand` там, где это действительно уместно.
- Не проглатывать исключения.
- Не вводить хаков и временных решений без явной необходимости.
- Перед созданием новых сущностей проверять, нет ли уже подходящих.
- Все пользовательские строки интерфейса должны проходить через локализацию.
- Основные цвета интерфейса должны идти через единый theme layer.
- Главное окно должно сохранять приоритет календаря как основного элемента навигации.

## Правила Git и GitHub

- Рабочая ветка разработки: `dev`.
- `master` не использовать как основную ветку активной разработки.
- Пуш выполняет пользователь вручную.
- `docs` должны входить в коммиты, если изменился код, архитектура, план, процесс или правила работы.

- Белая подложка стандартного `Calendar` гасится локальными `CalendarPanelStyle` и `CalendarItem` template в `MainWindow.xaml`; простые brush-ресурсы и `SystemColors.*` не убирали системный белый фон полностью.
- Редактор события больше не использует ручной ввод строк времени и 15-минутные интервалы: время выбирается отдельными селекторами часов, минут и секунд через `TimePartOptionViewModel`.
- `TimePartOptionViewModel` должен переопределять `ToString()` и возвращать `Title`, потому что закрытое состояние текущего `ComboBox` template может получить сам option-объект.
- Карточка события показывает `LocationDisplay`, если у `EventRecord` заполнено место.
- `EventRecord` теперь хранит `Status` и `ReminderMinutesBefore`; эти поля проходят через draft, data model, SQLite и редактор.
- Напоминания событий реализованы через планировщик `WindowsBalloonEventReminderService`, а транспорт по-прежнему вынесен в `IAppNotificationService`.
- Основной транспорт уведомлений теперь реализован через Windows App SDK `AppNotificationManager`.
- `WindowsBalloonAppNotificationService` сохранён как fallback, если Windows App SDK notifications недоступны в текущей среде или регистрация не удалась.
- Для Windows App SDK проект переведён на `net10.0-windows10.0.19041.0`, добавлены `WindowsPackageType=None` и runtime identifiers.
- Для рабочего notification flow на пользовательской машине требуется установленный пакет Windows App Runtime 1.8, включая `MicrosoftCorporationII.WinAppRuntime.Main.1.8` и `MicrosoftCorporationII.WinAppRuntime.Singleton`.
- Для задач добавлено собственное nullable-время напоминания `TaskReminderTime`; оно хранится отдельно от event-only поля `ReminderMinutesBefore`.
- Для всех типов записей добавлено несколько изображений-вложений через отдельную таблицу `record_attachments`; файл копируется в `%LocalAppData%\Taskloom\Media\Images`.
- Вложения изображений имеют `sort_order`; в редакторе их можно добавлять, удалять и переставлять, а карточка записи на главном экране показывает grid миниатюр и открывает конкретное изображение системным просмотрщиком по клику.
- Для всех типов записей добавлены audio attachments; редактор умеет импортировать несколько `mp3/wav/m4a/flac/wma/ogg`, а карточка записи показывает playlist с cover, play/pause, seek и открытием файла через shell.
- Полноценный `strip mode` с drag-scroll ещё не реализован; текущий завершённый этап — multiple images + grid layout.
- Описание записи в карточке умеет распознавать ссылки без изменения исходного текста: поддерживаются URI со схемой, домены без схемы, email и IPv4; открытие идёт через системный обработчик `UseShellExecute=true`.
- Tray mode реализован через `WindowsTrayService`: двойной клик по tray icon открывает окно, меню содержит `Открыть`, `Настройки`, `Выход`.
- Крестик главного окна теперь скрывает приложение в трей; реальное завершение идёт через `Выход`.
- Временная иконка приложения находится в `Assets/Icons/Taskloom.ico`; её можно заменить позже без изменения архитектуры.
- `AppSettings` хранит параметры главного окна: признак сохранённого placement, ширину, высоту и состояние окна.
- `MainWindow` не сохраняет координаты окна; сохранённый размер центрируется при старте, чтобы не зависеть от прошлой конфигурации мониторов.
- Закрытие `MainWindow` сохраняет placement асинхронно. Нельзя возвращать синхронное ожидание async-настроек в UI-потоке, это уже приводило к зависанию приложения при закрытии.
- В `ThemeService` подключены тринадцать тем: `WarmLight`, `NeutralLight`, `GrayLight`, `SoftDark`, `DeepDark`, `Windows11`, `Ubuntu`, `Windows7`, `MacOs`, `FrogGreen`, `VolcanicFire`, `CosmicCold`, `SnowWhite`.
- Все новые темы должны иметь полный набор `App.*Brush` ресурсов, включая status info/warning/success/danger и chip brushes.
- Стилизационные темы под ОС должны оставаться theme resources, а не отдельными шаблонами контролов или попыткой копировать системный UI.
- `ComboBox` и `ComboBoxItem` стилизованы глобально в `App.xaml`; если появятся новые popup/dropdown controls, их нужно отдельно проверить в тёмных темах.
- `DatePickerTextBox` имеет глобальный template в `App.xaml`; белую рамку стандартного шаблона нельзя возвращать.
- Popup-календарь `DatePicker` шаблонизирован в `App.xaml` через `ThemedPopupCalendarStyle`, `CalendarStyle` и `PART_Calendar`; без этих частей WPF может снова показать стандартный белый календарь.
- В `ThemedPopupCalendarStyle` `PART_CalendarItem` обязательно должен получать `Style="{TemplateBinding CalendarItemStyle}"`; иначе WPF вернёт стандартную белую рамку `CalendarItem`.
- В calendar button templates нельзя возвращать `ContentPresenter` для чисел. В главном календаре используем явный `TextBlock` с `Foreground="{DynamicResource App.TextPrimaryBrush}"`, потому что `TemplateBinding Foreground` не перебил системное состояние.
- Для главного `Calendar` стили кнопок дней должны подключаться через свойства `CalendarButtonStyle` и `CalendarDayButtonStyle`; implicit styles внутри `Calendar.Resources` не применялись к сгенерированным дням.
- В popup-календаре `DatePicker` внешний border намеренно прозрачный; видимую рамку должен задавать сам theme-aware calendar, а не стандартный белый popup.
- В тёмных темах primary/info акценты переведены в графитово-серую гамму, чтобы не было инородного сине-голубого цвета.
- В `MainWindow.xaml` календарь содержит локальные templates для `Calendar`, `CalendarItem`, `CalendarButton`, `CalendarDayButton`; это сделано ради читаемости и устранения системных светлых подложек.
- `SettingsWindow` и `RecordEditorWindow` тоже используют custom title bar через `WindowStyle=None` и `WindowChrome`; стандартную системную шапку для новых вспомогательных окон не возвращать без отдельного решения.
- Вспомогательные окна не должны сливаться с фоном: использовать внешнюю рамку `App.BorderStrongBrush`, внутренний фон `App.SurfacePrimaryBrush` и шапку `App.SurfaceSecondaryBrush`.
- `MainWindow` и `RecordEditorWindow` подключают `WindowMaximizeBoundsHelper`; без него безрамочное maximized-окно может уходить под панель задач.
- В настройках кнопка `Применить` только сохраняет язык и тему, но не закрывает окно. Закрытие выполняется крестиком в кастомной title bar.
- В редакторе записи блоки параметров конкретного типа должны скрываться целиком на уровне контейнера, а не только отдельных полей внутри блока.
- В длинных формах действия `Сохранить` и `Отмена` должны быть закреплены вне `ScrollViewer`; прокручиваться должна форма, а не критичные кнопки.

## На чём работа остановилась

Доменная модель, data model, SQLite schema, persistence-слой, прикладной слой, ViewModels, базовые Views, рефайнмент MVP и базовая локализация завершены.

После локализации были обнаружены и исправлены два критических дефекта:

1. Падение при открытии окна настроек.
2. Падение при отображении созданной задачи из-за некорректной WPF-привязки к read-only свойству `IsCompleted`.

Следующий шаг по плану:

1. Проверить визуально календарную панель, отсутствие белой подложки у стандартного `Calendar`, отображение места события и цветного статуса события в карточке.
2. Проверить вручную напоминание: создать событие на ближайшее время со статусом `Запланировано` и напоминанием `В момент события` или `За 5 минут`.
3. Проверить запуск главного окна: первый старт должен быть `Maximized`, последующие старты должны брать сохранённый размер и центрировать окно.
4. Проверить переключение всех тринадцати тем в окне настроек.
5. Проверить вспомогательные окна: системной шапки быть не должно, перетаскивание за кастомную верхнюю область должно работать, границы окна должны читаться во всех темах.
6. Проверить maximized-состояние главного окна и редактора: нижняя граница должна доходить до панели задач, но не уходить под неё.
7. Проверить настройки: `Применить` меняет язык/тему и оставляет окно открытым.
8. Проверить редактор записи: `Параметры задачи` видны только для задачи, `Параметры события` видны только для события.
9. Проверить редактор записи на обычном размере экрана: окно открывается нормальной высотой, кнопки снизу видны без прокрутки.
10. Проверить селекторы времени события: начало и конец выбираются как `HH:MM:SS`, а в закрытом поле не отображается сырое значение `TimeOnly`.
11. Проверить уведомления события: отдельно `Скоро событие` в момент напоминания и `Событие началось` в момент старта.
12. Проверить Windows App SDK notifications: уведомление должно появляться как системное и оставаться в центре уведомлений Windows 11.
13. Проверить tray mode: крестик скрывает окно, двойной клик по tray icon открывает, `Настройки` открывает окно настроек, `Выход` завершает приложение.
14. Проверить task reminders: pending-задача с включённым временем должна прислать одно уведомление на своей дате, completed-задача не должна уведомлять.

18. Следующим отдельным этапом остаётся `strip mode` с горизонтальным drag-scroll внутри контейнера.
19. Проверить link parsing в описании: `http/https/ftp/tg/mailto/file`, `youtube.com`, `tanki.su`, `192.168.34.165`, `user@example.com`, пунктуация после ссылки и несколько ссылок в одной строке.
20. После этого зафиксировать текущий срез отдельным коммитом или выбрать следующий функциональный этап.
21. При дальнейшей работе не возвращаться к локальным жёстким цветам мимо theme layer.

## Предпочтительное направление для data model

Нужно сохранить выразительность домена и при этом не усложнить MVP.

Уже выбран такой подход:

- одна таблица записей с общими полями
- поле типа записи
- nullable-поля для специфики типов там, где это оправдано для MVP

Это не означает, что домен должен стать плоским. Плоской может быть storage-модель, но не доменная.
