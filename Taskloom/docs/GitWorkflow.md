# Git и GitHub workflow

## Базовые правила

- Основная рабочая ветка проекта: `dev`.
- `master` не использовать как основную ветку активной разработки.
- Пуш в удалённый репозиторий выполняет пользователь вручную.
- Документация в `docs` является частью проекта и должна входить в коммиты вместе с кодом, если меняются архитектура, поведение, план, процесс или правила разработки.

## Правила подготовки коммита

- Перед добавлением файлов в staging всегда проверять `git status`.
- В staging добавлять только файлы, относящиеся к текущему шагу работы.
- Не добавлять в коммит `.idea`, `bin`, `obj`, временные файлы и локальные SQLite-артефакты.
- Перед коммитом проверять итоговый staged-состав через `git diff --cached --name-only`.
- Commit message оформлять на английском языке.
- Commit message должен быть коротким и прямо описывать итог изменения.
- Предпочтительный формат: одна короткая строка без emoji, лишней пунктуации и общих фраз вроде `update stuff`.

## Правила для помощника

Если пользователь просит "добавить к коммиту" или подготовить коммит:

1. Сначала проверить состояние репозитория.
2. Определить релевантные файлы текущего шага.
3. Обязательно включить `docs`, если изменения должны быть отражены в документации.
4. Не добавлять IDE-мусор и нерелевантные пользовательские файлы.
5. Если есть сомнительные или несвязанные изменения, явно сказать об этом пользователю.
6. Если пользователь просит текст коммита, предлагать краткий commit message на английском, соответствующий фактическому срезу изменений.

## GitHub

- Если GitHub-репозиторий ещё не создан, сначала создаётся удалённый проект, затем настраивается `origin`.
- После этого рабочая ветка `dev` пушится пользователем вручную.
- Если среда не позволяет автоматически создать GitHub-репозиторий, нужно честно зафиксировать блокер и подготовить локальный репозиторий к пушу без скрытых допущений.
