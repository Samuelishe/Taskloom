# Технические решения

## 2026-04-23

### Решение

Использовать один WPF-проект с логическим разделением по папкам.

### Причина

Для стартового этапа и MVP отдельные проекты в solution дадут лишнюю сложность без явной пользы.

### Последствия

- Ниже порог входа и быстрее развитие MVP.
- Потребуется дисциплина в разделении слоёв внутри одного проекта.

## 2026-04-23

### Решение

Организовать проект вокруг calendar-centered модели и нескольких типов записей.

### Причина

Продуктовая концепция требует расширяемой модели, а не упрощения всего до `Task`.

### Последствия

- Доменные сущности нужно проектировать как универсальные записи календаря.
- На уровне хранения и UI сразу нужно учитывать тип записи.

## 2026-04-23

### Решение

Сначала зафиксировать структуру и документацию, затем переходить к доменной модели.

### Причина

Это снижает риск хаотичного роста проекта и делает дальнейшие шаги последовательными.

### Последствия

- Первый рабочий шаг не включает реализацию MVP.
- Следующий этап должен быть посвящён доменной модели и связанным решениям.

## 2026-04-23

### Решение

Использовать базовую сущность `CalendarRecord` и специализированные доменные типы записей.

### Причина

Такой вариант лучше отражает концепцию calendar-centered organizer и не сводит всю систему к одной перегруженной записи с множеством nullable-полей.

### Последствия

- Домен остаётся выразительным и расширяемым.
- На следующем шаге потребуется аккуратно спроектировать data model и SQLite schema под полиморфную доменную модель.

## 2026-04-23

### Решение

Использовать одну таблицу `calendar_records` для хранения всех типов записей.

### Причина

Для MVP один table-per-hierarchy вариант даёт самую простую схему, удобную выборку по дате и предсказуемую реализацию репозиториев на Dapper.

### Последствия

- Storage-модель становится плоской, но домен остаётся типизированным.
- Репозиториям понадобится явное преобразование между `CalendarRecordDataModel` и доменными типами.
- Для специфики типов используются nullable-поля и SQL `CHECK`-ограничения.

## 2026-04-23

### Решение

Использовать отдельные компоненты `SqliteConnectionFactory` и `SqliteDatabaseInitializer`, а репозиторий реализовать поверх Dapper.

### Причина

Такое разделение сохраняет простой и читаемый infrastructure-слой: подключение, инициализация схемы и доступ к данным не смешиваются между собой.

### Последствия

- Следующий слой сервисов может использовать готовый доменный репозиторий без знания деталей SQLite.
- Для маппинга между domain и storage добавлена явная логика преобразования в репозитории.

## 2026-04-23

### Решение

Использовать `CalendarRecordDraft` и отдельный `CalendarRecordService` как прикладной API для UI-сценариев.

### Причина

Это не даёт будущим ViewModels напрямую конструировать доменные типы и держит правила создания и редактирования записей в одном месте.

### Последствия

- UI будет работать с draft-моделью, а не с инфраструктурой или SQL-структурами.
- Следующий шаг с окнами и ViewModels станет прямолинейнее.

## 2026-04-23

### Решение

Выполнять композицию зависимостей в `App`, а не создавать ViewModels прямо из XAML.

### Причина

`MainWindowViewModel` зависит от сервисов и инициализации SQLite, поэтому XAML-конструирование здесь уже слабое решение.

### Последствия

- Старт приложения становится явным и управляемым.
- Следующие ViewModels можно подключать к сервисам без временных заглушек и service locator-подхода.

## 2026-04-23

### Решение

Использовать ветку `dev` как рабочую ветку разработки и включать `docs` в обычные коммиты проекта.

### Причина

Проект уже опирается на документацию как на часть рабочего процесса, архитектуры и правил продолжения сессий.

### Последствия

- Изменения кода и документации должны коммититься согласованно.
- Перед коммитом нужно явно проверять staged-состав, чтобы туда не попадали IDE-файлы и локальный мусор.
