# Архитектура Taskloom

## Структура проекта

На старте используется один WPF-проект `Taskloom` с логическим разделением по папкам:

- `Assets` - статические ресурсы интерфейса
- `Common` - общие вспомогательные типы
- `Data` - модели хранения и SQL-артефакты
- `Domain` - доменные сущности и правила
- `Infrastructure` - инфраструктурные реализации
- `Presentation` - ViewModels и Views
- `Services` - прикладные сервисы
- `docs` - проектная документация внутри корня WPF-проекта для удобной работы в IDE

## Документы восстановления контекста

Для продолжения работы после потери сессии используется `docs/ContinuationGuide.md`. В нём фиксируются текущие правила, стадия проекта и следующий шаг.

Для git-процесса используется `docs/GitWorkflow.md`.

## Git-организация проекта

- Основная рабочая ветка проекта: `dev`.
- Документация в `docs` считается частью исходников проекта и коммитится наравне с кодом.
- `.gitignore` должен исключать IDE-мусор, build outputs и локальные артефакты SQLite, но не должен исключать проектную документацию.

## Правила локализации и настроек

- Все пользовательские строки интерфейса должны храниться вне XAML и ViewModels.
- Локализация должна работать через отдельные файлы языков.
- На старте поддерживаются `ru-RU` и `en-US`.
- Настройки приложения должны храниться отдельно от SQLite-данных предметной области.
- Переключение языка должно открываться из UI без верхнего меню.
- Для входа в настройки используется кнопка с иконкой шестерёнки в главном окне.
- Тема оформления также должна управляться через настройки приложения.

## Правила композиции главного окна и тем

- Главное окно должно оставаться calendar-centered не только логически, но и визуально.
- Нельзя искусственно увеличивать контейнер календаря, если сам календарный контрол от этого не становится полезнее.
- При нехватке места второстепенные элементы должны перестраиваться вокруг календаря, а не выталкивать навигацию за пределы окна.
- Состояние выбранной записи должно быть визуально очевидным и заметно отличаться от hover-состояния.
- Основные цвета приложения должны идти через theme resources.
- Выбранная цветовая схема должна управляться из настроек приложения.
- Если статус задачи меняется прямо из списка, это должен быть явный интерактивный control, а не декоративный бейдж.

## Слои

### Domain

Содержит основные сущности предметной области и правила, не зависящие от UI и хранения.

### Data

Содержит модели хранения и описание структуры SQLite.

На текущем этапе слой данных использует одну storage-модель `CalendarRecordDataModel`, которая отражает общую таблицу `calendar_records`.

### Infrastructure

Содержит технические реализации доступа к БД и вспомогательные инфраструктурные компоненты.

На текущем этапе здесь находятся:

- загрузка JSON-файлов локализации и источник строк для WPF
- фабрика SQLite-подключений
- вычисление путей хранения файла БД
- инициализация схемы базы данных
- хранение настроек приложения в отдельном JSON-файле
- применение тем оформления через `ResourceDictionary`
- SQLite/Dapper реализация репозитория записей

### Services

Содержит прикладные сценарии и координацию работы домена, репозиториев и UI.

На текущем этапе в этом слое находятся:

- `ICalendarRecordRepository` как абстракция persistence-доступа
- `ICalendarRecordService` как прикладной API для UI
- `CalendarRecordService` как реализация сценариев CRUD, фильтрации и подготовки черновиков
- `CalendarRecordDraft` как модель редактора записи

В следующем этапе сюда будут добавлены сервис локализации и сервис настроек приложения.
Эти сервисы уже добавлены и используются presentation-слоем.

### Presentation

Содержит WPF Views и ViewModels. Бизнес-логика во View не допускается.

На текущем этапе здесь находятся:

- `MainWindowViewModel` для выбранной даты, фильтрации и списка записей
- `RecordEditorViewModel` для черновика создания и редактирования
- вспомогательные presentation-модели списка и фильтра
- `MainWindow` как главный экран с календарём и списком записей
- `RecordEditorWindow` как отдельное окно редактора записи
- адаптивный карточный layout списка записей с вычислением ширины карточек через converter
- `calendar-first` компоновка `MainWindow`
- selected-state карточек записей с заметной цветовой полосой и усиленным фоном
- перевод основных цветов окон и контролов на theme resources
- быстрый toggle статуса задач должен идти через `MainWindowViewModel` и прикладной сервис, а не через code-behind

В следующем этапе presentation-слой должен быть переведён с жёстких строк на локализуемые ключи и получить окно настроек.
Этот перевод выполнен для текущего UI.

## Доменные ожидания

- Базовая сущность должна описывать запись календаря, а не только задачу.
- Тип записи должен оставаться расширяемым.
- Модель должна позволять развивать приложение в сторону richer editor, linked records и recurring items.

## Доменная модель

### Выбранный вариант

Используется абстрактная базовая сущность `CalendarRecord` и специализированные типы:

- `TaskRecord`
- `NoteRecord`
- `EventRecord`
- `DaySummaryRecord`

### Почему выбран этот вариант

- Общие свойства записи остаются в одном месте: идентификатор, дата, заголовок, описание, тип.
- Правила конкретных типов можно держать рядом с самими типами.
- Следующий шаг со схемой SQLite остаётся прямолинейным: можно хранить общий набор полей и тип записи, не теряя доменной выразительности.

### Альтернатива

Плоская универсальная запись с большим числом необязательных полей была бы проще для старта, но она быстро размоет границы между типами и перенесёт проверки из домена в UI и persistence-слой.

### Базовые доменные правила

- У любой записи обязателен непустой заголовок.
- Заголовок и текст нормализуются через `Trim`.
- `EventRecord` обязан иметь временной диапазон, где `EndTime > StartTime`.
- `TaskRecord` хранит признак завершения.

## Модель хранения и SQLite schema

### Выбранный вариант

Для persistence-слоя используется одна таблица `calendar_records`.

Она хранит:

- общие поля записи
- тип записи
- nullable-поля для особенностей `TaskRecord` и `EventRecord`

### Почему выбран этот вариант

- Для MVP это самая простая и читаемая схема.
- Выборка записей по дате и фильтрация по типу делаются одним запросом без `JOIN`.
- Dapper-репозитории на такой схеме будут прямолинейными.
- Домен остаётся выразительным, потому что плоской является только storage-модель.

### Ограничения схемы

- `DaySummaryRecord` ограничен одной записью на дату через уникальный partial index.
- Для `EventRecord` на уровне БД зафиксировано наличие `start_time` и `end_time`.
- Для `TaskRecord` хранится `is_completed`.

## Persistence-слой

### Что реализовано

- `SqliteConnectionFactory` открывает подключения к файлу SQLite.
- `TaskloomPaths` определяет стандартный путь к локальной базе данных.
- `SqliteDatabaseInitializer` применяет `CreateSchema.sql`.
- `SqliteCalendarRecordRepository` выполняет CRUD и маппинг между `CalendarRecordDataModel` и доменными типами.

### Почему так

- Подключение и инициализация БД изолированы от будущих ViewModels и сервисов.
- Репозиторий уже работает с доменной моделью, а не отдаёт наружу storage-структуры.
- Для текущего масштаба проекта отдельный unit of work или сложный abstraction layer не нужен.

## Прикладной слой

### Что реализовано

- Сервис `CalendarRecordService` строит и сохраняет доменные записи на основе `CalendarRecordDraft`.
- Фильтрация по типу записи проходит через прикладной API, а не напрямую из будущего UI в репозиторий.
- Для редактирования существующей записи сервис умеет превращать доменную сущность обратно в `CalendarRecordDraft`.

### Почему так

- ViewModel не должна знать, какой доменный тип нужно создать для `Task`, `Note`, `Event` или `DaySummary`.
- Draft-модель упрощает работу окна редактора и снижает связность UI с доменным слоем.

## ViewModels

### Что реализовано

- `App` выполняет композицию зависимостей и инициализацию базы при старте.
- `MainWindowViewModel` работает через `ICalendarRecordService`.
- В `MainWindowViewModel` уже заложены выбранная дата, фильтр по типу, список записей и команды загрузки, удаления и подготовки черновика.
- `RecordEditorViewModel` изолирует UI-редактирование от доменных конструкторов.

### Почему так

- Будущие WPF Views можно строить поверх уже готового состояния и команд.
- Инициализация persistence-слоя не протекает в XAML и code-behind окна.

## Views

### Что реализовано

- `MainWindow` показывает календарь, выбранную дату, фильтр и список записей.
- `MainWindow.xaml.cs` выполняет только оркестрацию открытия и закрытия окна редактора.
- `RecordEditorWindow` работает как отдельное окно для создания и редактирования записи.

### Почему так

- Требование MVP про отдельное окно редактора соблюдено.
- Бизнес-логика сохранения не уехала во View, а осталась во `ViewModel` и сервисах.

## Рефайнмент MVP

### Что усилено

- Удаление записи подтверждается на уровне UI.
- Двойной клик по записи открывает её редактирование.
- Ввод времени в редакторе валидируется при сохранении, а не ломает binding во время ввода.
- Startup приложения перехватывает ошибки и сообщает их пользователю.
- Список записей больше не опирается на стандартное визуальное выделение `ListBoxItem`.
- Карточки записей перестраиваются по ширине окна и переходят между одной, двумя и тремя колонками.
- Ширина карточки теперь ограничена сверху, поэтому одиночная запись не растягивается на всю область списка.
- Хедер, блок выбранной даты, календарный контейнер и кнопки действий приведены к общей визуальной системе без добавления новой UI-инфраструктуры.
- Календарная колонка усилена по размеру, потому что календарь является центральным элементом приложения.
- Основные окна и базовые контролы переведены на theme resources с возможностью переключения схемы из настроек.
- В карточках задач удалён неинтерактивный `CheckBox`; состояние задачи показывается как текстовый статус, а изменение остаётся в редакторе записи.
- Для карточек задач добавлен интерактивный status chip с быстрым переключением состояния через `MainWindowViewModel` и прикладной сервис.
- Type, info и status chips приведены к общей визуальной системе через общие ресурсы приложения и согласованные semantic palettes тем.
- Главное окно использует кастомную title bar область через `WindowChrome`, чтобы сохранить нативный resize/snap и убрать системный заголовок.
- Бренд и текущая дата вынесены в кастомную title bar, а левая панель начинается с рабочего блока выбранной даты и настроек.
- Кнопка настроек размещена в кастомной title bar, потому что относится ко всему окну, а не к блоку выбранной даты.

## Следующий архитектурный шаг

- Текущая локализационная инфраструктура может дальше масштабироваться на новые окна и post-MVP функции.
- Следующие шаги должны опираться на уже существующий локализационный и settings-контур, а не обходить его.
- Для цветовых схем следует использовать `ResourceDictionary` как нативный механизм WPF, а не вводить JSON-темы без необходимости.
- Выбранная тема должна храниться в настройках приложения рядом с языком, но отдельно от SQLite.

## Ключевые решения на текущем этапе

- Один проект вместо раннего дробления solution на несколько assembly.
- Папочная, а не проектная сегментация на старте.
- MVVM как базовый способ организации presentation-слоя.
