# Архитектура Taskloom

## Структура проекта

На старте используется один WPF-проект `Taskloom` с логическим разделением по папкам:

- `Assets` - статические ресурсы интерфейса
- `Common` - общие вспомогательные типы
- `Data` - модели хранения и SQL-артефакты
- `Domain` - доменные сущности и правила
- `Infrastructure` - инфраструктурные реализации
- `Presentation` - ViewModels и Views
- `Services` - прикладные сервисы
- `docs` - проектная документация внутри корня WPF-проекта для удобной работы в IDE

## Документы восстановления контекста

Для продолжения работы после потери сессии используется `docs/ContinuationGuide.md`. В нём фиксируются текущие правила, стадия проекта и следующий шаг.

Для git-процесса используется `docs/GitWorkflow.md`.

## Git-организация проекта

- Основная рабочая ветка проекта: `dev`.
- Документация в `docs` считается частью исходников проекта и коммитится наравне с кодом.
- `.gitignore` должен исключать IDE-мусор, build outputs и локальные артефакты SQLite, но не должен исключать проектную документацию.

## Зависимости среды выполнения

- Приложение собирается под `net10.0-windows10.0.19041.0`.
- Для обычного запуска пользователю нужен установленный .NET 10 Desktop Runtime.
- Для Windows App SDK notifications в центре уведомлений нужен установленный Windows App Runtime 1.8.
- Если Windows App Runtime 1.8 отсутствует или его пакеты установлены неполно, `AppNotificationManager` может не зарегистрироваться, и приложение должно перейти на fallback через `WindowsBalloonAppNotificationService`.

## Правила локализации и настроек

- Все пользовательские строки интерфейса должны храниться вне XAML и ViewModels.
- Локализация должна работать через отдельные файлы языков.
- На старте поддерживаются `ru-RU` и `en-US`.
- Настройки приложения должны храниться отдельно от SQLite-данных предметной области.
- Переключение языка должно открываться из UI без верхнего меню.
- Для входа в настройки используется кнопка с иконкой шестерёнки в главном окне.
- Тема оформления также должна управляться через настройки приложения.
- Настройки языка, темы и политики очистки должны применяться сразу при выборе, без отдельной кнопки `Применить`.

## Правила композиции главного окна и тем

- Главное окно должно оставаться calendar-centered не только логически, но и визуально.
- Нельзя искусственно увеличивать контейнер календаря, если сам календарный контрол от этого не становится полезнее.
- При нехватке места второстепенные элементы должны перестраиваться вокруг календаря, а не выталкивать навигацию за пределы окна.
- Состояние выбранной записи должно быть визуально очевидным и заметно отличаться от hover-состояния.
- Снятие выделения записи должно быть доступно кликом по пустым и неинтерактивным областям окна.
- Основные цвета приложения должны идти через theme resources.
- Выбранная цветовая схема должна управляться из настроек приложения.
- Если статус задачи меняется прямо из списка, это должен быть явный интерактивный control, а не декоративный бейдж.

## Слои

### Domain

Содержит основные сущности предметной области и правила, не зависящие от UI и хранения.

### Data

Содержит модели хранения и описание структуры SQLite.

На текущем этапе слой данных использует одну storage-модель `CalendarRecordDataModel`, которая отражает общую таблицу `calendar_records`.

### Infrastructure

Содержит технические реализации доступа к БД и вспомогательные инфраструктурные компоненты.

На текущем этапе здесь находятся:

- загрузка JSON-файлов локализации и источник строк для WPF
- фабрика SQLite-подключений
- вычисление путей хранения файла БД
- инициализация схемы базы данных
- хранение настроек приложения в отдельном JSON-файле
- применение тем оформления через `ResourceDictionary`
- SQLite/Dapper реализация репозитория записей

### Services

Содержит прикладные сценарии и координацию работы домена, репозиториев и UI.

На текущем этапе в этом слое находятся:

- `ICalendarRecordRepository` как абстракция persistence-доступа
- `ICalendarRecordService` как прикладной API для UI
- `CalendarRecordService` как реализация сценариев CRUD, фильтрации и подготовки черновиков
- `CalendarRecordDraft` как модель редактора записи

В следующем этапе сюда будут добавлены сервис локализации и сервис настроек приложения.
Эти сервисы уже добавлены и используются presentation-слоем.

### Presentation

Содержит WPF Views и ViewModels. Бизнес-логика во View не допускается.

На текущем этапе здесь находятся:

- `MainWindowViewModel` для выбранной даты, фильтрации и списка записей
- `RecordEditorViewModel` для черновика создания и редактирования
- вспомогательные presentation-модели списка и фильтра
- `MainWindow` как главный экран с календарём и списком записей
- `RecordEditorWindow` как отдельное окно редактора записи
- адаптивный карточный layout списка записей с вычислением ширины карточек через converter
- `calendar-first` компоновка `MainWindow`
- selected-state карточек записей с утолщённой левой границей и усиленным фоном
- перевод основных цветов окон и контролов на theme resources
- быстрый toggle статуса задач должен идти через `MainWindowViewModel` и прикладной сервис, а не через code-behind

В следующем этапе presentation-слой должен быть переведён с жёстких строк на локализуемые ключи и получить окно настроек.
Этот перевод выполнен для текущего UI.

## Доменные ожидания

- Базовая сущность должна описывать запись календаря, а не только задачу.
- Тип записи должен оставаться расширяемым.
- Модель должна позволять развивать приложение в сторону richer editor, linked records и recurring items.

## Доменная модель

### Выбранный вариант

Используется абстрактная базовая сущность `CalendarRecord` и специализированные типы:

- `TaskRecord`
- `NoteRecord`
- `EventRecord`
- `DaySummaryRecord`

### Почему выбран этот вариант

- Общие свойства записи остаются в одном месте: идентификатор, дата, заголовок, описание, тип.
- Правила конкретных типов можно держать рядом с самими типами.
- Следующий шаг со схемой SQLite остаётся прямолинейным: можно хранить общий набор полей и тип записи, не теряя доменной выразительности.

### Альтернатива

Плоская универсальная запись с большим числом необязательных полей была бы проще для старта, но она быстро размоет границы между типами и перенесёт проверки из домена в UI и persistence-слой.

### Базовые доменные правила

- У любой записи обязателен непустой заголовок.
- Заголовок и текст нормализуются через `Trim`.
- `EventRecord` обязан иметь временной диапазон, где `EndTime > StartTime`.
- `TaskRecord` хранит признак завершения.
- `TaskRecord` может хранить собственное nullable-время напоминания.

## Модель хранения и SQLite schema

### Выбранный вариант

Для persistence-слоя используется таблица `calendar_records` и отдельная таблица `record_attachments`.

Она хранит:

- общие поля записи
- тип записи
- nullable-поля для особенностей `TaskRecord` и `EventRecord`
- attachment-метаданные вынесены в отдельную таблицу
- файловые ресурсы хранятся отдельно от SQLite в `%LocalAppData%\Taskloom\Records\<record-id>\...`
- внутри каталога записи используются подпапки `images`, `audio`, `audio-covers` и metadata-файл `record.json`

### Почему выбран этот вариант

- Для MVP это самая простая и читаемая схема.
- Выборка записей по дате и фильтрация по типу делаются одним запросом без `JOIN`.
- Dapper-репозитории на такой схеме будут прямолинейными.
- Домен остаётся выразительным, потому что плоской является только storage-модель.

### Ограничения схемы

- `DaySummaryRecord` ограничен одной записью на дату через уникальный partial index.
- Для `EventRecord` на уровне БД зафиксировано наличие `start_time` и `end_time`.
- Для `TaskRecord` хранятся `is_completed` и nullable `task_reminder_time`.
- Изображения записи хранятся как несколько attachments типа `Image`; порядок отображения задаётся полем `sort_order`.
- Аудиофайлы записи хранятся как несколько attachments типа `Audio`; для них в `record_attachments` сохраняются `display_title`, `duration_seconds`, `preview_relative_path` и общий `sort_order`.

## Persistence-слой

### Что реализовано

- `SqliteConnectionFactory` открывает подключения к файлу SQLite.
- `TaskloomPaths` определяет стандартный путь к локальной базе данных.
- `TaskloomPaths` определяет локальный каталог `%LocalAppData%\Taskloom\Records` и подпути ресурсов для каждой записи.
- `SqliteDatabaseInitializer` применяет `CreateSchema.sql`.
- `SqliteCalendarRecordRepository` выполняет CRUD и маппинг между `CalendarRecordDataModel`, `RecordAttachmentDataModel` и доменными типами.
- `RecordImageStorageService` импортирует `jpg/jpeg/png/bmp/gif`, возвращает метаданные attachment и сохраняет файлы в каталог конкретной записи.
- `RecordAudioStorageService` импортирует `mp3/wav/m4a/flac/wma/ogg`, читает title/duration/cover через `TagLibSharp` и сохраняет локальные аудиофайлы и обложки в каталог конкретной записи.
- `RecordResourceMetadataService` поддерживает metadata-файл `record.json` рядом с ресурсами записи и удаляет каталог записи целиком при полном удалении записи.
- Presentation-слой пока использует grid layout миниатюр; горизонтальная drag-лента остаётся следующим отдельным UX-этапом.
- Для описания записи используется presentation-only парсинг ссылок: исходный текст `Details` не меняется, а `TextBlock` рендерит `Run/Hyperlink` поверх исходной строки.
- Для воспроизведения аудио используется единый `AudioPlaybackService` на базе WPF `MediaPlayer`; карточка записи показывает playlist по audio-attachments, а одновременно играет только один трек.

### Почему так

- Подключение и инициализация БД изолированы от будущих ViewModels и сервисов.
- Репозиторий уже работает с доменной моделью, а не отдаёт наружу storage-структуры.
- Для текущего масштаба проекта отдельный unit of work или сложный abstraction layer не нужен.

## Прикладной слой

### Что реализовано

- Сервис `CalendarRecordService` строит и сохраняет доменные записи на основе `CalendarRecordDraft`.
- Фильтрация по типу записи проходит через прикладной API, а не напрямую из будущего UI в репозиторий.
- Для редактирования существующей записи сервис умеет превращать доменную сущность обратно в `CalendarRecordDraft`.
- `CalendarRecordService` при сохранении поддерживает metadata-файл ресурсов записи, а при удалении записи очищает и SQLite, и каталог `%LocalAppData%\Taskloom\Records\<record-id>`.
- Сервис также поддерживает startup cleanup старых записей по выбранной политике из настроек.

### Почему так

- ViewModel не должна знать, какой доменный тип нужно создать для `Task`, `Note`, `Event` или `DaySummary`.
- Draft-модель упрощает работу окна редактора и снижает связность UI с доменным слоем.

## ViewModels

### Что реализовано

- `App` выполняет композицию зависимостей и инициализацию базы при старте.
- `MainWindowViewModel` работает через `ICalendarRecordService`.
- В `MainWindowViewModel` уже заложены выбранная дата, фильтр по типу, список записей и команды загрузки, удаления и подготовки черновика.
- `RecordEditorViewModel` изолирует UI-редактирование от доменных конструкторов.

### Почему так

- Будущие WPF Views можно строить поверх уже готового состояния и команд.
- Инициализация persistence-слоя не протекает в XAML и code-behind окна.

## Views

### Что реализовано

- `MainWindow` показывает календарь, выбранную дату, фильтр и список записей.
- `MainWindow.xaml.cs` выполняет только оркестрацию открытия и закрытия окна редактора.
- В карточках записи обрезаемые строки должны отдавать полный текст через tooltip, а не раздувать layout по контенту.
- `RecordEditorWindow` работает как отдельное окно для создания и редактирования записи.

### Почему так

- Требование MVP про отдельное окно редактора соблюдено.
- Бизнес-логика сохранения не уехала во View, а осталась во `ViewModel` и сервисах.

## Рефайнмент MVP

### Что усилено

- Удаление записи подтверждается на уровне UI.
- Двойной клик по записи открывает её редактирование.
- Время события выбирается через отдельные контролы часов, минут и секунд, а не вводится вручную строкой.
- Startup приложения перехватывает ошибки и сообщает их пользователю.
- Список записей больше не опирается на стандартное визуальное выделение `ListBoxItem`.
- Карточки записей перестраиваются по ширине окна и переходят между одной, двумя и тремя колонками.
- Ширина карточки теперь ограничена сверху, поэтому одиночная запись не растягивается на всю область списка.
- Хедер, блок выбранной даты, календарный контейнер и кнопки действий приведены к общей визуальной системе без добавления новой UI-инфраструктуры.
- Календарная колонка усилена по размеру, потому что календарь является центральным элементом приложения.
- Основные окна и базовые контролы переведены на theme resources с возможностью переключения схемы из настроек.
- Поддерживаются тринадцать тем: базовые светлые/тёмные схемы, стилизационные схемы Windows 11, Ubuntu, Windows 7, macOS и авторские темы Frog, Fire, Cosmic, Snow.
- `ComboBox` и `ComboBoxItem` имеют собственные theme-aware templates, потому что стандартный WPF control отдельно рисует закрытое состояние и popup системными цветами.
- `DatePicker` и внутренний `DatePickerTextBox` имеют theme-aware стили и template, потому что стандартное поле даты отдельно наследует системные цвета и белую рамку.
- Popup-календарь `DatePicker` использует `CalendarStyle` и обязательную часть `PART_Calendar` с theme-aware templates для `Calendar` и `CalendarItem`, чтобы не возвращался стандартный белый календарь.
- Popup-календарь `DatePicker` не должен иметь внешний border вокруг `Calendar`; белая рамка стандартного popup убрана на уровне template.
- Размер и состояние главного окна сохраняются в `AppSettings`; при первом запуске окно открывается `Maximized`, при следующих запусках восстановленный размер центрируется на рабочей области экрана.
- Сохранение placement главного окна при закрытии выполняется асинхронно без блокировки UI-потока.
- В карточках задач удалён неинтерактивный `CheckBox`; состояние задачи показывается как текстовый статус, а изменение остаётся в редакторе записи.
- Для карточек задач добавлен интерактивный status chip с быстрым переключением состояния через `MainWindowViewModel` и прикладной сервис.
- Type, info и status chips приведены к общей визуальной системе через общие ресурсы приложения и согласованные semantic palettes тем.
- Карточка события показывает место, если оно заполнено, через presentation-модель `RecordListItemViewModel`.
- `EventRecord` хранит статус события и время напоминания до начала события.
- `TaskRecord` хранит отдельное nullable-время напоминания на дату задачи.
- В редакторе события статус и напоминание выбираются через локализованные `ComboBox`.
- В редакторе задачи напоминание включается отдельно и задаётся собственным временем, не связанным с event-only полями.
- Напоминания MVP реализованы через `WindowsBalloonEventReminderService` и `NotifyIcon.ShowBalloonTip`, без добавления тяжёлой notification-инфраструктуры.
- Транспорт локальных уведомлений вынесен в `IAppNotificationService`; основная реализация использует Windows App SDK `AppNotificationManager`, а `WindowsBalloonAppNotificationService` оставлен только как fallback.
- Планировщик событий отправляет два разных уведомления: напоминание до события и уведомление о начале события.
- Главное окно использует кастомную title bar область через `WindowChrome`, чтобы сохранить нативный resize/snap и убрать системный заголовок.
- Вспомогательные окна также используют `WindowStyle=None` и кастомную title bar область; окно редактора сохраняет resize через `WindowChrome`, окно настроек остаётся фиксированного размера.
- Безрамочные окна, которые можно разворачивать, должны подключать `WindowMaximizeBoundsHelper`, чтобы maximized-состояние ограничивалось рабочей областью монитора и не уходило под панель задач.
- Во вспомогательных окнах кастомная title bar содержит только заголовок и кнопку закрытия, потому что minimize/maximize для них не являются основным сценарием.
- Вспомогательные окна обязаны иметь собственную контрастную оболочку: внешнюю рамку на `App.BorderStrongBrush`, тело на `App.SurfacePrimaryBrush` и шапку на `App.SurfaceSecondaryBrush`.
- Окно настроек применяет язык, тему и политику очистки сразу при выборе; закрытие окна выполняется отдельным крестиком в кастомной title bar.
- Для опасных режимов очистки всех старых записей окно настроек должно запрашивать подтверждение перед сохранением значения.
- Подтверждения удаления записи и dangerous cleanup mode должны использовать собственное themed-окно приложения, а не системный `MessageBox`.
- В длинных вспомогательных окнах нижняя панель действий должна быть закреплена вне прокручиваемой области, чтобы кнопки не пропадали при недостаточной высоте окна.
- Карточка записи должна показывать компактный бейдж времени создания; он остаётся слабоконтрастным и не конкурирует с type/status chips.
- Бренд и текущая дата вынесены в кастомную title bar, а левая панель начинается с рабочего блока выбранной даты и настроек.
- Кнопка настроек размещена в кастомной title bar, потому что относится ко всему окну, а не к блоку выбранной даты.
- Календарная панель не должна содержать лишние вложенные контейнеры: статус, навигация по дню и календарь размещаются внутри одного внешнего блока.
- Левая календарная панель использует устойчивую структуру: статус сверху и единый центральный прозрачный блок `Calendar + navigation buttons`.
- Стандартный WPF `Calendar` использует локально переопределённые templates для `Calendar` и `CalendarItem`, потому что стандартный шаблон рисовал белую скруглённую подложку глубже, чем позволяли исправить brush-ресурсы.
- Кнопки дней календаря имеют локальные templates с явными `TextBlock`, привязанными к `TemplateBinding Foreground`, чтобы тёмные темы не наследовали нечитаемые системные цвета.
- В редакторе события время выбирается через отдельные селекторы `HH:MM:SS`; доменный тип остаётся `TimeOnly?`.

## Следующий архитектурный шаг

- Текущая локализационная инфраструктура может дальше масштабироваться на новые окна и post-MVP функции.
- Следующие шаги должны опираться на уже существующий локализационный и settings-контур, а не обходить его.
- Для цветовых схем следует использовать `ResourceDictionary` как нативный механизм WPF, а не вводить JSON-темы без необходимости.
- Выбранная тема должна храниться в настройках приложения рядом с языком, но отдельно от SQLite.
- Новая тема должна содержать полный набор существующих `App.*Brush` ресурсов, иначе часть UI останется с цветами другой темы или системными цветами.
- Темы, стилизованные под ОС, являются визуальными интерпретациями палитр, а не попыткой копировать системные контролы или поведение этих ОС.
- Авторские темы должны оставаться полноценными theme dictionaries и задавать не только фон/акцент, но и semantic palettes для chips/status.
- Тёмные темы используют нейтрально-серые primary/info акценты, без сине-голубого доминирования.
- Параметры главного окна должны храниться в `AppSettings`, а не в SQLite, потому что это пользовательская настройка приложения, а не предметные данные.
- Политика очистки записей также хранится в `AppSettings`, а не в SQLite.
- В WPF code-behind нельзя блокировать UI-поток через `GetAwaiter().GetResult()` для async-операций настроек или файлового ввода-вывода.
- Новые поля события, требующие хранения, нужно добавлять только после явного решения по SQLite schema и миграциям.
- Если потребуется полноценный modern toast, нужно заменить только реализацию `IEventReminderService`, сохранив домен и ViewModels.
- Для Windows 11 используется `AppNotificationManager` из Windows App SDK, чтобы уведомления попадали в центр уведомлений.
- Поскольку Taskloom остаётся unpackaged WPF-приложением, Windows App Runtime 1.8 сейчас считается внешней зависимостью среды, а не частью дистрибутива приложения.
- Tray mode должен быть отдельной инфраструктурной подсистемой жизненного цикла приложения, а не побочным эффектом сервиса напоминаний.
- Tray mode реализован через `WindowsTrayService`; он владеет единственным `NotifyIcon`, context menu и временной иконкой приложения.
- Balloon notification transport использует `NotifyIcon` из `WindowsTrayService`, чтобы не создавать вторую иконку в трее.
- Закрытие главного окна пользователем скрывает приложение в трей; реальное завершение выполняется через пункт `Выход`.
- Напоминания задач добавлены через отдельное поле `task_reminder_time`; поле события `reminder_minutes_before` не переиспользуется для задач.
- Автоматическая очистка старых записей запускается на старте приложения после загрузки настроек и инициализации БД.
- Сбой auto-cleanup не должен валить весь startup; такие ошибки нужно только логировать.
- Опасные режимы очистки могут удалять вообще все записи старше порога, включая заметки и day summaries; поэтому они не должны включаться без явного подтверждения пользователя.
- Новые вспомогательные окна должны использовать общий подход `WindowStyle=None` + `WindowChrome` + собственная title bar, а не возвращать стандартный системный заголовок.
- Если вспомогательное окно содержит длинную форму, нужно задавать нормальный стартовый размер и ограничивать высоту рабочей областью экрана, а не открывать маленькое окно с критичными кнопками внутри скролла.
- Если новое окно с `WindowStyle=None` поддерживает maximize, нужно подключить helper обработки `WM_GETMINMAXINFO`, иначе окно может развернуться под панель задач.
- Время события не должно отображаться в UI как сырое `TimeOnly`/nullable-значение; пользовательский ввод должен идти через форматированные option-модели.
- Доступ к `settings.json` внутри процесса должен быть сериализован; параллельные apply-операции и сохранение placement окна не должны конфликтовать между собой.
- Быстрые последовательные переключения языка и темы не должны вызывать каскадное повторное применение настроек или визуальное мигание тем.
- В карточках записей текстовый контент должен оставаться top-aligned даже в рядах с карточками разной высоты; пустое пространство допустимо только снизу карточки.
- В persistence-модели записи должен храниться `created_utc`, чтобы UI не вычислял время создания эвристически.
- Для audio attachments допустимо хранить дополнительные nullable-метаданные `album_title` и `genre`; при их отсутствии UI не должен резервировать отдельный заметный блок.

## Ключевые решения на текущем этапе

- Один проект вместо раннего дробления solution на несколько assembly.
- Папочная, а не проектная сегментация на старте.
- MVVM как базовый способ организации presentation-слоя.
